MrKwiz deployment plan

Deploy one codebase to Cloudflare and Supabase without paying for extra environments yet.

This repo is already shaped for a Cloudflare Worker with static assets and edge API handlers, backed by Supabase. The cheapest stable deployment setup is two remote environments only: stage to staging and prod to production. Feature branches should run CI, but not auto-deploy to a live database.

Cloudflare Worker + static assets Supabase staging + prod GitHub Actions as deploy orchestrator
Decision: use GitHub Actions as the single deployment control plane, not a split setup where Cloudflare auto-builds from Git while Supabase migrations run elsewhere. One system should run tests, apply migrations, deploy the Worker, and then run smoke tests in sequence.

Recommended Shape

Local + feature branches

Develop against the local Supabase stack. Feature branches run tests only. Do not attach feature branches to a shared hosted database on the free plan.

stage branch

Deploy to a hosted staging Supabase project and a staging Cloudflare Worker such as mrkwiz-staging.

prod branch

Deploy to the production Supabase project and a production Cloudflare Worker such as mrkwiz.

Why not preview deployments for every PR? Supabase free tier does not include branching, only allows two active projects, and pauses inactive projects after one week. That makes branch-per-PR databases unreliable and unsafe. Keep previews to CI results only, or static-only previews with no live writes.

Initial Deploy

  1. Create the branch model. Add long-lived stage and prod branches if you do not already use them. Protect both. Require pull requests and passing checks on both.
  2. Create two Supabase projects. Make one staging project and one production project. Free tier allows only two active projects, so those are your whole hosted fleet.
  3. Create the first remote schema from code, not from dashboard clicks. Keep supabase/migrations as the source of truth. If you already changed a hosted project manually, pull that state into migrations before you automate deployments.
  4. Create two Cloudflare Worker targets. This repo already uses wrangler.toml with static assets from dist. Extend that config with separate [env.staging] and [env.production] blocks so the same code deploys to two Worker names and, later, two custom domains.
  5. Create GitHub environments. Add staging and production in GitHub, then store environment-specific secrets with the same names in both places.

Repository-level secrets

Shared by all deploy jobs.

CLOUDFLARE_ACCOUNT_ID
CLOUDFLARE_API_TOKEN
SUPABASE_ACCESS_TOKEN

Environment-level secrets

Set these separately in GitHub environments staging and production.

SUPABASE_PROJECT_ID
SUPABASE_DB_PASSWORD
SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY
APP_TOKEN_SECRET
SMOKE_ADMIN_KEY

Those environment secrets match the runtime and test surfaces already present in the repo. The Worker itself needs SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, and APP_TOKEN_SECRET. Your staging smoke suite also needs a stable SMOKE_ADMIN_KEY.

Recommended workflow set

ci.yml

Run on pull requests. Install, build, run unit tests, function tests, and any cheap static validation. No remote deploy.

deploy-staging.yml

Run on push to stage. Apply Supabase migrations to staging, deploy the Worker to Cloudflare staging, then run the deployed smoke suite.

deploy-production.yml

Run on push to prod. Require GitHub Environment approval for production. Apply migrations, deploy production Worker, then verify the deployed homepage responds cleanly.

feature/* -> pull request -> ci only
    stage     -> auto deploy staging -> run staging smoke tests
    prod      -> manual approval -> auto deploy production

Subsequent Deploys

  1. Build features on a short-lived branch against local Supabase.
  2. If the change affects schema, create or update a migration in supabase/migrations and verify locally with npm run supabase:db:reset or the safer local DB test harness already in the repo.
  3. Open a pull request into stage. CI must pass before merge.
  4. Merging to stage should be enough to trigger staging deployment automatically. That job should run in this order: tests already green, supabase db push to staging, wrangler deploy --env staging, then npm run test:smoke:api:staging against the deployed URL.
  5. After staging looks good, open a PR from stage to prod.
  6. Merge to prod. GitHub should require production approval, then run the production deployment automatically and finish with a narrow live probe.
What pushing to a branch should mean here: pushing to a feature branch only buys you feedback, pushing to stage buys you a staging release, and pushing to prod buys you a production release. That is the safest approximation of "just push and let CI/CD handle it" while staying inside free-tier limits.

Limits You Are Likely To Hit First

Supabase free tier

  • Only 2 active projects. That is why the plan uses staging and production only.
  • 500 MB database size. Quiz snapshots, responses, and answer history can grow faster than expected if you retain every iteration forever.
  • 5 GB egress and 1 GB file storage. This app looks light now, but chart-heavy usage or uploaded media would make this matter.
  • No backups and no branching. Treat migrations and exports as your safety net.
  • Projects are paused after 1 week of inactivity. Staging can wake slowly or surprise you after idle periods.
  • 1 day log retention. Investigate incidents quickly or you lose the easy trail.

Cloudflare free tier

  • 100,000 Worker requests per day across the account. Staging traffic, production traffic, and smoke tests all count.
  • 10 ms CPU time per request. Network wait time does not count, but heavy parsing or large in-memory transforms can trip this.
  • 128 MB memory per isolate and 50 subrequests per invocation. You are well within that now, but it matters if one request fans out.
  • 64 environment variables per Worker. Fine for this app, but avoid secret sprawl.
  • 20,000 static asset files per Worker version. Vite output is nowhere near this today.

The first practical upgrade trigger is usually Supabase, not Cloudflare: needing backups, wanting preview databases, or outgrowing the two-project ceiling.

One-Time Implementation Checklist

  • Add stage as the staging branch.
  • Add [env.staging] and [env.production] to wrangler.toml.
  • Create staging and production Supabase projects.
  • Create GitHub environments and secrets.
  • Add the three GitHub Actions workflows. This repo now includes ci.yml, deploy-staging.yml, and deploy-production.yml.
  • Seed or bootstrap one quiz in staging so deployed smoke tests have an admin key to exercise.
  • Protect stage and prod with required checks.
